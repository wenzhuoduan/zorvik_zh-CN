你已经学了很多：请求与响应、环境、测试、集合、Mock 和负载测试。在真实世界里，这些会在同一天汇合：**发布日**，API 上线、真实应用开始调用它的那天。

好的团队不指望发布顺利。他们走一份 **清单**，而清单上的每一项，你现在都能在 Zorvik 里做。

## 发布清单

```flow
契约 -> 集合 -> 检查 -> 冒烟运行 -> 负载测试 -> 交接
```

| # | 项目 | 在 Zorvik 里 | 完成标准…… |
|---|---|---|---|
| 1 | **契约** | 一份大家都认可的 OpenAPI 文档 | 它已在仓库里并通过评审 |
| 2 | **集合** | **导入…** 契约；一个环境里放着 `baseUrl` | 每个操作都是一个已保存的请求 |
| 3 | **契约检查** | 每个响应上的 **Matches the API spec** 测试 | 真实 API 给出文档中写的回答 |
| 4 | **冒烟运行** | **运行…** 这个文件夹 | 一次点击，所有请求都通过 |
| 5 | **性能** | 一个带阈值的负载测试 | 运行通过：p95 和错误率都在目标内 |
| 6 | **交接** | 从契约生成的 Mock，以及 **复制为 cURL 或代码…** | 应用团队不用问你就能开工 |

逐条说几句：

- **契约。** OpenAPI 文档描述每一条路径、每一个参数和每一种回答。它是后端对应用许下的承诺。
- **集合与环境。** 导入契约会把每个操作变成一个已保存的请求。服务器地址放在 `baseUrl` 变量里，所以同一批请求既能打在笔记本上，也能打在 *预发* 服务器（生产环境的测试副本）或生产环境上。
- **契约检查。** 从文档导入的请求，对每个回答都自带一个测试：**Matches the API spec**。它检查状态码在文档里有记载，以及 JSON 正文符合文档描述的形状。后端一旦偏离契约，这个测试就变红。
- **冒烟运行。** *冒烟测试* 是快速过一遍主要功能，看看有没有哪里着火。把整个文件夹跑一遍，正是这件事。
- **性能。** 一个短的、带阈值的负载测试，把「够快吗？」变成绿色或红色的答案。
- **交接。** 应用团队拿到一个可以对着开发的 Mock，以及用他们自己语言写好的代码片段：Android 用 Kotlin，iOS 用 Swift，Web 用 JavaScript，脚本用 Python。

> [!note] 可以这样想……
> 飞行员的起飞前检查单。飞行员已经飞过一千次，可每一次飞行仍然按同样的顺序检查燃油、襟翼和仪表。不是因为他们会忘，而是因为清单能把「我觉得没问题」变成「我检查过，没问题」。

## 让它可重复

这份清单不是一次性的仪式。把契约、集合、负载测试和 Mock 都留在工作区里，再把工作区放进 Git。下一次发布，你几分钟就能把同样的检查再跑一遍，有哪里变差了，红色会告诉你。

> [!tip] 先预发，后生产
> 所有检查都对着预发服务器跑。只有上线后的冒烟运行才把清单指向生产环境；没有计划和许可，永远不要对生产环境做负载测试。

下一课，你会为一个真实（嗯，几乎真实）的发布走完这整份清单。那是你的最终任务。

**什么时候用得上：** 团队说「我们周四上线」，而你能拿出证据说「它准备好了」。
