AI 模型自己只会写文字。要查天气、读工单或者查数据库，它需要 **工具**：一些小函数，它可以请应用去执行。**模型上下文协议（MCP）** 就是把这类工具提供给 Claude、ChatGPT、Cursor、VS Code 等 AI 应用的开放标准。

## 它解决的问题

在 MCP 之前，每个 AI 应用接入工具都各有一套办法。手里有一个好 API 的团队，得为每个应用分别写连接器，而每个应用又得认识每个工具。五个应用配十个工具，最多就是五十个集成，每个都略有不同，每个都用自己的方式出故障。

MCP 把它变成两侧各 *一次* 连接：应用说一次 MCP，工具说一次 MCP，然后任何应用都能用任何工具。

> [!note] 可以这样想……
> 一个 USB-C 接口。你的笔记本不需要为每个牌子的充电器、硬盘或显示器准备专用插口。只要有那个插头就能用。MCP 就是 AI 应用的这种插头。

## 谁是谁

```flow
AI 模型 -> 宿主应用 -> MCP 客户端 -[JSON-RPC]-> MCP 服务器 -> 你的 API 或数据
```

- **宿主** 就是你使用的 AI 应用（Claude Desktop、某个 IDE、某个编码 Agent）。
- 它内部有一个 **MCP 客户端**，与每个 **MCP 服务器** 各保持一条连接。
- **服务器** 告诉别人自己能做什么，并回答调用。它往往只是包在你现有 API 外面的一层薄壳。

## 服务器提供什么

| 提供项 | 是什么 | 例子 |
|---|---|---|
| **工具** | 模型可以调用的函数，每个都带输入 schema（JSON Schema） | `get_forecast(city)` |
| **资源** | 应用可以按 URI 读取的文档 | `docs://readme`、`users://42` |
| **提示词** | 让用户挑选的消息模板 | `code_review(language)` |

## 它们怎么对话

MCP 消息是 **JSON-RPC**：小小的 JSON 对象，带有 `method`、`params` 和一个 `id`，回答里会重复这个 `id`。

```sequence
participants: 客户端, 服务器
客户端 -> 服务器: initialize（版本、能力）
服务器 --> 客户端: 它的名称、版本和能力
客户端 -> 服务器: tools/list
服务器 --> 客户端: 工具的名称、说明和输入 schema
客户端 -> 服务器: tools/call get_forecast {city: "Oslo"}
服务器 --> 客户端: content: "Sunny, 21 °C"
```

它们通过两种 **传输方式** 之一传递：

- **stdio**：应用在你电脑上把服务器当作程序启动，通过它的标准输入输出交换一行行 JSON。大多数本地服务器都是这样工作的。
- **Streamable HTTP**：服务器住在某个 URL（`https://…/mcp`）上；每条消息是一次 HTTP POST，回答以 JSON 或事件流的形式返回。更早的服务器用 **HTTP+SSE**。

## 为什么要测 MCP 服务器？

人会读 API 文档，发现不对再试一次。模型不会：它凭 **说明** 挑工具，凭 **schema** 填参数，而且常常没人看着。所以一段含糊的说明、一个什么胡话都放行的 schema、一句只写着「failed」的错误，或者一个卡住的工具，都会直接变成一个做错事的 Agent。

Zorvik 让你看到 Agent 看到的原样：连上一个服务器，列出它提供的东西，用自己的参数发起调用，查看每一条消息，并像测任何 API 一样测它的回答。而当你在做 MCP *客户端* 时，一个 Mock MCP 服务器就能让你不用真服务器也能测它。

## 什么时候用得上……

- 你为自己的产品搭了一个 MCP 服务器，想在 AI 应用之前把每个工具都验一遍，
- 某个 Agent 行为不对，你需要看看服务器到底回答了什么，
- 你在写 AI 应用或 Agent，需要一个回答可预测（包括失败）的服务器。
